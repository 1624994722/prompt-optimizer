# 代码场景 Prompt 模板库

针对编程高频任务的优化模板与示例。使用时：匹配最接近的场景 → 套骨架 → 把用户原始信息填入 → 按 SKILL.md 第 6 步压缩。

## 场景索引

1. 实现新功能
2. 修 bug / 报错排查
3. 代码审查
4. 重构与性能优化
5. 解释代码 / 写文档
6. 写脚本 / 自动化
7. 架构与技术选型

---

## 1. 实现新功能

骨架：

```
任务：实现【功能一句话描述】。
技术栈：【语言+版本 / 框架+版本 / 关键依赖】
环境：【OS / 运行环境 / 相关已有代码结构】
需求细节：
- 输入：【格式与示例】
- 输出：【格式与示例】
- 边界情况：【必须处理的异常场景】
约束：【兼容性 / 性能要求 / 禁止使用的库 / 代码风格】
输出：完整可运行代码 + 简短使用说明；关键设计决策用注释说明。
完成前对照上方需求细节与边界情况逐项自检。
```

**示例**

输入（口语）："帮我写个东西，能把文件夹里一堆图片压缩一下，太大了微信发不出去。"

输出（优化后）：

```
任务：写一个 Python 命令行脚本，批量压缩指定文件夹中的图片。
技术栈：Python 3.10+，仅用 Pillow。
需求细节：
- 输入：文件夹路径（命令行参数），处理其中所有 jpg/png/webp，含子文件夹
- 输出：在原文件夹下新建 compressed/ 目录存放结果，保持原文件名和目录结构
- 压缩目标：单张输出 ≤ 1MB，最长边 ≤ 1920px，JPEG 质量从 85 起逐步下调直至达标
- 边界情况：跳过已达标的文件；损坏文件报错但继续处理；最后打印处理统计
输出：完整可运行脚本 + 一行使用示例。
```

## 2. 修 bug / 报错排查

骨架：

```
任务：定位并修复以下 bug。
环境：【语言/框架/依赖版本、OS】
现象：【期望行为 vs 实际行为，一句话】
报错信息/日志：
```
【完整粘贴，不要截断】
```
相关代码：
```
【最小可复现代码，已脱敏】
```
已尝试：【做过的排查及结果】
输出：
1. 根因分析（按可能性排序）
2. 修复后的代码（标注改动点）
3. 一句话说明修复原理
```

要点：**报错信息和版本号是排障 prompt 里最值钱的内容**，务必保留完整；引导用户提供"最小可复现"而非整个项目。

## 3. 代码审查

骨架：

```
任务：审查以下【语言】代码。
背景：【这段代码的用途 / 所属项目类型】
代码：
```
【粘贴】
```
审查重点（按优先级）：
1. 正确性与潜在 bug
2. 安全问题（注入、越权、敏感信息）
3. 性能隐患
4. 可读性与风格
输出：按严重度（🔴阻塞/🟡建议/🔵可选）列出问题，每条给出：位置、问题、修改建议代码。
约束：无问题的方面直接说"无问题"，不要硬凑。
```

约束：【对外接口不可变 / 行为必须等价 / 兼容 Python 3.8】
代码：
```
【粘贴】
```
输出：
1. 优化后完整代码
2. 改动清单（每条说明：改了什么、为什么、收益）

## 7. 架构与技术选型

骨架：

```
任务：为以下项目做技术选型/架构设计建议。
项目：【一句话说明做什么】
规模：【用户量级 / 数据量级 / 团队人数与经验】
硬约束：【预算 / 已有系统 / 必须兼容的技术 / 上线时间】
候选方案（如有）：【A vs B】
输出：
1. 推荐方案及核心理由（不超过 3 条）
2. 对比表（维度：开发效率/性能/运维成本/生态/团队匹配）
3. 主要风险与缓解措施
约束：只推荐与团队规模匹配的简单方案，反对过度设计。
```

## 代码通用要点

- **版本号即信息量**：Python 3.8 和 3.12 的答案完全不同，版本、框架、OS 是必填槽位。
- 要求"完整可运行代码"，避免 AI 给伪代码片段。
- 要求"标注改动点"，长代码 diff 才看得懂。
- 结尾追加一句"完成前对照验收标准逐项自检"——零成本，官方验证的可靠纠错手段。
- 多文件/多成分上下文（代码+报错+需求+约束混杂）时，用 `<code>/<error>/<requirements>/<constraints>` 等 XML 标签分区，标签名全文一致且成对闭合。
- 给 AI 一个**可验证的验收标准**（输出示例、性能数字、测试用例），回答质量立刻提升。
- 粘贴代码前提醒用户脱敏（密钥、内网地址、个人信息）。
